# 1. Axis meanings

## `sampledData`

In `prepareRadialVibeDataForGridding2_3.m`, the raw data are transformed and eventually reshaped as:

```matlab
Z = permute(Z, [1 4 3 2]);
...
Z = reshape(Z, [nLines*nPartitions*nSamples, nTransformedChannels]);
```

The intended axes before flattening are:

```text
readout sample × partition × spoke × coil
```

Therefore:

```matlab
sampledData
```

has dimensions:

```text
[nReadout*nPartition*nSpokes, nCoil]
```

with the flattened ordering:

```text
readout fastest
partition next
spoke next
coil as the second matrix dimension
```

Thus, when the reshape assumptions are correct:

```matlab
data4(readout, partition, spoke, coil)
```

does mean:

```text
one readout sample
one Cartesian partition
one radial spoke
one coil
```

However, the meaning of `nPartition` depends on which value is used:

- `q.image.NPar`: number of acquired partitions;
- `s.m{end}.param.Meas{1}.MEAS.sKSpace.lPartitions`: protocol/full partition count.

Those are not necessarily equal.

## `kSpaceLocations`

The trajectory is generated from:

```matlab
[iiPartition, iiLine] = ndgrid(0:nPartitions-1, 0:nLines-1);
```

and:

```matlab
kz = (double(iiPartition(:)) - cPartition) / ...
     nPartitions / dSliceResolution;
```

The flattened trajectory is:

```matlab
kSpaceLocations = [kx ky kz];
```

with dimensions:

```matlab
[nReadout*nPartition*nSpokes, 3]
```

After:

```matlab
locations4 = reshape(kSpaceLocations, ...
    [nReadout, nPartition, nSpokes, 3]);
```

the intended interpretation is:

```matlab
locations4(readout, partition, spoke, coordinate)
```

where coordinate 1, 2, and 3 are `kx`, `ky`, and `kz`.

## `spokeIndex`

`iiSpoke` is generated by repeating the spoke/line index across readout samples and partitions. After reshaping:

```matlab
spoke4(readout, partition, spoke)
```

should be constant across readout and partition for each spoke block.

That is what this validation checks:

```matlab
spoke4(:) == expectedSpokes(:)
```

## `dataZ4`

The current code performs:

```matlab
dataZ4 = fftshift( ...
    ifft(ifftshift(data4, 2), [], 2), ...
    2) * sqrt(nPartition);
```

If `data4` has partition dimension 58, then `dataZ4` also has partition dimension 58.

The IFFT does not create additional z samples:

```text
[nReadout, 58, nSpokes, nCoil]
    →
[nReadout, 58, nSpokes, nCoil]
```

Likewise, if the input has partition dimension 96 after zero-padding, then the result has 96 z samples.

## `selectedZ`

The current code:

```matlab
selectedZ = dataZ4(:, zIndex, ...);
```

selects one index in the output of the partition IFFT.

Therefore:

- with a 58-point IFFT, valid `zIndex` values are 1:58;
- with a 96-point IFFT, valid `zIndex` values are 1:96.

A value such as `zIndex = 50` is not intrinsically “image slice 50.” It means “the 50th sample in the current partition-IFFT output.”

## `kxyFrame`

This is formed as:

```matlab
kxy4 = locations4(:, :, :, 1) + ...
       1i * locations4(:, :, :, 2);

kxyFrame = kxy4(:, 1, 1:nFrame * nbSpokesPerFrame);
```

Because the in-plane trajectory is expected to repeat across partitions, selecting partition 1 is appropriate only after validating that the in-plane trajectory is partition-independent.

# 2. Where the 58-to-96 behavior occurs

The relevant code is in `prepareRadialVibeDataForGridding2_3.m`.

The function defines:

```matlab
nCollectedPartitions = double(q.image.NPar);
nPartitions = s.m{end}.param.Meas{1}.MEAS.sKSpace.lPartitions;
```

Then it computes:

```matlab
nFourierPartitions = double(nPartitions - q.image.NPar);
```

and applies:

```matlab
Z = padarray(Z, [0 nFourierPartitions 0 0], 0, 'pre');
```

After the earlier permutation:

```matlab
Z = permute(Z, [1 4 3 2]);
```

the second dimension is the partition dimension. Therefore, this padding is applied along partitions, before the final flattening.

## Important cases

### Case A: acquired partitions = 58, protocol partitions = 96

Then:

```matlab
q.image.NPar = 58
nPartitions = 96
nFourierPartitions = 38
```

and the data are padded to:

```text
[nReadout, 96, nSpokes, nCoil]
```

with 38 zero planes inserted before the acquired partition data.

The trajectory is also generated using:

```matlab
nPartitions = 96
```

so the output trajectory has 96 partition positions.

In this case, the slice-wise STM preparation should use:

```matlab
nPartition = 96
```

not 58.

### Case B: acquired partitions = 58, protocol partitions = 58

Then:

```matlab
nFourierPartitions = 0
```

and no partition padding occurs. The slice-wise preparation produces only 58 z samples.

The conventional 96-slice volume then comes from the requested reconstruction geometry and subsequent 3-D gridding/resizing, not from the same 96-point partition-domain representation.

## Padding location

The existing code pads:

```matlab
before the partition-domain IFFT
```

and uses:

```matlab
'pre'
```

not symmetric padding.

That is important. The correct equivalent is not automatically:

```matlab
padarray(data4, [0 19 0 0], 0, 'both')
```

The existing code’s actual convention is:

```matlab
padarray(data4, [0 nFourierPartitions 0 0], 0, 'pre')
```

provided that `nFourierPartitions = nPartitions - q.image.NPar`.

The exact interpretation depends on how the acquired partitions are positioned relative to the full protocol partition grid. The code’s trajectory generation and the padding operation must be considered together.

# 3. How the conventional 3-D path obtains its image dimensions

In `loadPrepareGARSOSData.m`, the target image dimensions are independently selected, commonly as:

```matlab
imageSize = [224 224 96];
```

The oversampled grid is then:

```matlab
gridSize = ceil(griddingParams.gridOversamplingFactor .* imageSize);
```

In `GpuReconstructur20181008.m`, the gridding constructor receives:

```matlab
gridSize
imageSize
sampleCoordinates
```

The samples are accumulated onto the 3-D Cartesian grid, followed by:

```matlab
A = ifftn(A);
```

and an internal resize/deapodization step involving `shiftAndResize`.

Thus, the final spatial z dimension is determined by the requested:

```matlab
imageSize(3)
```

rather than necessarily by the number of acquired partitions.

This means there are potentially two distinct situations:

```text
Full protocol partition grid = 96
Acquired partition count      = 58
Requested image z size        = 96
```

In that common case, the intended single-slice preparation should probably operate on the 96-plane padded partition grid, then perform a 96-point partition IFFT.

But if the protocol partition count is actually 58, then the conventional 96-slice volume is a separate spatial resampling/zero-filling result and cannot be reproduced by merely selecting index 50 from a 58-point IFFT.

# 4. Is the current IFFT expression correct?

The expression:

```matlab
fftshift(ifft(ifftshift(data4, 2), [], 2), 2)
```

is mathematically reasonable for centered partition data when:

1. the partition samples are ordered in the same centered convention expected by the transform;
2. the partition dimension already has the full desired Fourier length;
3. the pre-padding convention matches the acquisition’s partition location.

But it is not sufficient by itself to solve the 58-versus-96 issue.

The correct conceptual sequence is:

```text
acquired partition data
    ↓
place acquired data into the correct full partition grid
    ↓
apply the same centering convention as the conventional reconstruction
    ↓
perform the full-length partition IFFT
    ↓
select the desired image-space z index
```

If the protocol partition count is 96, the likely intended implementation is:

```matlab
data4 = reshape(sampledData, ...
    [nReadout, 96, nSpokes, nCoil]);

dataZ4 = fftshift( ...
    ifft(ifftshift(data4, 2), [], 2), ...
    2) * sqrt(96);

selectedZ = dataZ4(:, zIndex96, ...);
```

where the 96-dimensional `data4` already includes the exact pre-padding performed by `prepareRadialVibeDataForGridding2_3.m`.

If only 58 samples are available and the full partition count is genuinely 58, then producing 96 z samples requires an explicit 58-to-96 Fourier-domain embedding. However, that embedding cannot safely be inferred from the current `prepareGARSOSSliceDataForMCNUFFT` function alone.

# 6. Why slice 50 could resemble reference slice 18

Your observation is consistent with a coordinate-system mismatch, but it is not enough to identify a unique cause.

The most likely explanations, in order, are:

## 1. 58-index output compared against a 96-index reference volume

If the STM path produces a 58-point z array but the reference is 96 slices, then:

```matlab
zIndex = 50
```

does not correspond to:

```matlab
referenceVolumeC.A(:, :, 50)
```

There is no valid direct index equivalence.

## 2. Wrong partition-grid length

If the conventional reconstruction uses a 96-plane partition grid but the STM path uses a 58-point IFFT, the two outputs have different z sampling intervals and coordinate origins.

## 3. Pre-padding placement

The existing preprocessing uses pre-padding:

```matlab
padarray(..., 'pre')
```

If the STM path omits this or applies symmetric padding instead, the z origin and phase ramp change.

## 4. Partition centering

The trajectory uses:

```matlab
cPartition = floor(nPartitions / 2);
```

For even lengths, the exact centered index convention matters. A one-index or half-grid offset can produce a spatial shift.

## 5. FFT shift convention

The explicit slice-wise transform may be shifted relative to the internal 3-D gridding convention.

## 6. Reversed z orientation

The physical transform `CA` may contain a z sign flip. A reversal could make slice 50 correspond approximately to a slice near the opposite end of the volume.

## 7. Different physical z spacing/origin

The 96-slice image geometry is defined by `ArrayVolume` fields:

```matlab
R
v
r0
```

and by centered resizing. A numerical array index is not itself a physical coordinate.

The approximate mapping from slice 50 to slice 18 is therefore plausible as the result of a combination of offset, reversal, and differing sampling grids. It should not be attributed to `fftshift` alone.

# 8. ArrayVolume geometry

The repository’s `ArrayVolume` representation separates array indexing from physical coordinates.

Relevant fields are:

```matlab
referenceVolumeA.A
referenceVolumeA.R
referenceVolumeA.v
referenceVolumeA.r0
```

In `centeredArrayVolumeResize.m`, resizing preserves the physical center and updates the origin:

```matlab
r0 = a.r0 + a.R * diag(a.v) * (cOld - cNew)';
```

In `resampleArrayVolumeToSame.m`, interpolation is performed by mapping target voxels through the physical geometry fields.

Therefore:

```matlab
referenceVolumeC.A(:, :, zIndex)
```

is meaningful only together with:

```matlab
referenceVolumeC.R
referenceVolumeC.v
referenceVolumeC.r0
```

The desired STM slice should correspond to the same physical plane, not merely the same integer array index.

A physical coordinate for slice index `zIndex` can be computed using the image-volume convention:

```matlab
index0 = [xIndex - 1; yIndex - 1; zIndex - 1];
r = referenceVolumeC.r0 + ...
    referenceVolumeC.R * diag(referenceVolumeC.v) * index0;
```

The exact index origin should be confirmed against the project’s `ArrayVolume` convention, but the essential point is that `R`, `v`, and `r0` determine the physical mapping.

# 9. Sensitivity-map handling

The shared loader `loadPrepareGARSOSData.m` does:

1. periodic extension of the channel sensitivity maps;
2. scanner-origin adjustment;
3. resampling to `referenceVolumeC`;
4. storage as:
   ```matlab
   prepared.sensitivityMaps
   ```

Those maps are therefore already represented on the requested target image grid, commonly:

```matlab
[Nx, Ny, 96, nCoil]
```

This means the current extraction:

```matlab
prepared.sensitivityMaps(:, :, zSlice, :)
```

is appropriate only when `zSlice` is an index in the same 96-slice target geometry.

It is not automatically correct if the radial data have been transformed into a native 58-point z grid.

There are two consistent options:

## Option A: use a 96-plane partition/IFFT grid

If preprocessing pads the acquired data to 96 partitions, then use:

```matlab
zIndex = 1:96
```

and extract sensitivity maps at the corresponding target-grid index:

```matlab
sensitivityMapsSlice = prepared.sensitivityMaps(:, :, zIndex, :);
```

## Option B: use a native 58-plane partition/IFFT grid

Then the sensitivity maps must be sampled or interpolated onto the 58-point physical z coordinates produced by the partition IFFT. Simply using:

```matlab
prepared.sensitivityMaps(:, :, zIndex, :)
```

would generally be wrong because those maps are on the 96-slice target geometry.

# 11. Recommended processing chain

## If protocol partitions are 96

The correct chain is likely:

```text
58 acquired partition samples
    ↓
pre-pad to 96 exactly as prepareRadialVibeDataForGridding2_3 does
    ↓
generate/use 96-point kz trajectory
    ↓
apply the validated centered partition convention
    ↓
96-point inverse FFT
    ↓
select zIndex in 1:96
    ↓
extract sensitivity maps from the same 96-slice geometry
    ↓
perform 2-D radial STM reconstruction
```

The key is that `sampledData`, `kSpaceLocations`, and `nPartition` must all refer to the same 96-plane partition grid.

## If protocol partitions are 58

Then the correct chain is instead:

```text
58 acquired partition samples
    ↓
58-point inverse FFT
    ↓
58 native z samples
    ↓
map each native z sample to physical coordinates
    ↓
interpolate sensitivity maps/reference data at those coordinates
    ↓
select by physical z coordinate
```

The 58-point output should not be directly indexed against a 96-slice reference volume.

If a 96-point z output is required, an explicit Fourier-domain embedding or spatial resampling must be introduced, but it must be derived from the actual physical FOV, voxel spacing, and partition locations.

```matlab
if zIndex < 1 || zIndex > nFourierPartitions
    error('zIndex is outside the full z grid.');
end

selectedZ = dataZ4(:, zIndex, ...
    1:nFrame * nbSpokesPerFrame, :);
```

But this code is valid only if the trajectory and flattened sample data have been generated using that same full partition dimension. It should not be inserted blindly into the current function, because the current `sampledData` may already include the padding.

In fact, if `prepareRadialVibeDataForGridding2_3.m` has already applied the padding, then padding again would be incorrect.

The first implementation change should therefore be to carry explicit metadata such as:

```matlab
prepared.nAcquiredPartitions
prepared.nFourierPartitions
prepared.nPrePaddingPartitions
```

rather than inferring these later.

# 14. Validation experiment

The most reliable validation is to compare the single-slice data against the existing conventional reconstruction in physical z coordinates.

## Step 1: reconstruct a conventional volume

Use the validated 3-D GAR-SOS reconstruction to obtain:

```matlab
conventionalVolume
```

on the same target grid as:

```matlab
referenceVolumeC
```

## Step 2: generate every candidate STM z slice

For each candidate z index:

```matlab
for zIndex = 1:nZ
    % prepare a candidate slice
    % reconstruct or form a comparable image
end
```

## Step 3: compare using normalized correlation

For candidate STM slice `stmImage` and conventional slice `referenceImage`:

```matlab
a = abs(stmImage(:));
b = abs(referenceImage(:));

a = a - mean(a);
b = b - mean(b);

correlation = real(a' * b) / ...
    sqrt(real(a' * a) * real(b' * b));
```

Or, if the images are on exactly the same geometry:

```matlab
nrmse(zIndex) = norm(stmImage(:) - referenceImage(:)) / ...
    norm(referenceImage(:));
```

The NRMSE calculation should only be used after correcting for:

- intensity scaling;
- possible global phase;
- coil-combination differences;
- coordinate orientation;
- physical z alignment.

A more robust comparison allows a global complex scale:

```matlab
alpha = referenceImage(:)' * stmImage(:) / ...
    (stmImage(:)' * stmImage(:));

error = norm(referenceImage(:) - alpha * stmImage(:)) / ...
    norm(referenceImage(:));
```

## Step 4: compare physical coordinates

For each STM candidate slice, record its physical z coordinate. Then compare the candidate to the conventional/reference slice with the closest physical coordinate—not merely the same integer index.

This will distinguish:

- wrong array indexing;
- reversed z orientation;
- constant z offset;
- different z sampling spacing;
- incorrect padding.

# Bottom line

The central issue is real:

```text
58 acquired partitions
```

must not automatically be treated as:

```text
96 image-space slices.
```

But the repository’s preprocessing may already convert 58 acquired partitions into a full 96-plane Fourier grid through:

```matlab
nFourierPartitions = lPartitions - q.image.NPar;
Z = padarray(Z, [0 nFourierPartitions 0 0], 0, 'pre');
```

Therefore, the first thing to establish is whether:

```matlab
q.image.NPar
```

is 58 while:

```matlab
lPartitions
```

is 96.

If so, the slice-wise STM path must use the already-padded 96-plane representation and must not reshape it as 58 partitions.

If both values are 58, then the current 58-point IFFT cannot be directly compared against a 96-slice reference volume. In that case, the STM path needs a physically consistent z resampling or Fourier-domain embedding before selecting a reference-grid slice.
